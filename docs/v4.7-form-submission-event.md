## Summary

The forms now notify the parent website (WordPress, Webflow, etc.) when a submission has been sent to Salesforce, so the parent site's Google Tag Manager can fire GA4 and/or Google Ads conversions. The release also adds a test page for the embed and event flow, a Salesforce debug mode, a reCAPTCHA fix for non-prod orgs, and refreshed UAT IDs.

**Backward compatible:** when the iframe URL has no `?form_id=`, the data sent to Salesforce is the same as before.

---

## 1. How it works

```
Parent site (their GTM)            Our iframe (Vercel)                      Salesforce
───────────────────────            ───────────────────                      ──────────
<iframe src=".../LeadForm/index.html?form_id=contact-us">
                                   visitor submits
                                   forms.js adds form_id, form_type,
                                   campaign, sid to retURL ───────── POST ──▶ Web-to-Lead / Case
                                                                             redirect to retURL
                                   thankyou.html?form_id=…&sid=… ◀───────────┘
                                   postMessage ──┐
listener validates origin + payload ◀────────────┘
dataLayer.push({ event: "form_submission", … })
GTM fires GA4 / Ads tags
```

- **Form page (`forms.js`):** if `?form_id=` is present, the form adds `form_id`, `form_type`, `campaign` and a generated `sid` to the **`retURL` query string** on submit. No form fields are added.
- **Thank-you page (`thankyou.html`, via `forms.js`):** if those params are present and the page is inside an iframe, it sends one `postMessage` to the parent.
- **Parent:** the listener from section 5 of the handover doc validates the message and pushes it to `dataLayer`. The parent site owns the GTM / GA4 / Ads configuration. We don't need their `G-…` ID.

### Known limitation

Web-to-Lead never confirms that the record was created. It redirects to `retURL` even when the lead is rejected (reCAPTCHA, validation rules, wrong org). **"Success" therefore means the visitor was redirected to the thank-you page.** This is known and accepted, and it's being handled separately.

## 2. Message contract (version 1)

```javascript
{
  source: "haas-marketing-forms",
  message_type: "form_submission",
  version: 1,
  status: "success",
  form_id: "contact-us",          // from ?form_id=
  form_type: "lead",              // "case" when the form has an orgid field (CaseForm)
  campaign: "lupomax",            // from ?campaign=, or null
  submission_id: "<uuid>"         // generated at submit; stable across thank-you reloads
}
```

No personal data or form contents are included.

## 3. URL parameters added

| Parameter | Where | Effect |
|---|---|---|
| `form_id` | Form iframe URL | Turns on tracking. Without it, the console logs `[haas-forms] No ?form_id= …` and nothing else changes. |
| `debug=1` | Form or test page URL | Adds Salesforce `debug=1` and `debugEmail` (from `debug_email` in `configs/<org>.json`). Salesforce shows its debug page instead of redirecting, so **no event fires in debug mode**. |

Existing parameters (`campaign`, `template`, `branch`, `org`, field prefill) are unchanged.

## 4. Behaviour changes in `forms.js`

| Change | Details |
|---|---|
| **Same-origin `retURL`** | On load, `retURL` is rewritten to the `thankyou.html` of the deployment serving the form (prod, staging, preview, localhost). It only touches our own `/thankyou.html` and keeps path and query. On prod the value is unchanged. It applies to all forms, with or without `form_id`. |
| **Tracking params on submit** | Only with `?form_id=`. Wrapped in try/catch, so a failure never blocks the submit. |
| **postMessage from thank-you page** | Only when `sid` + `form_id` are present and the page is framed. The target origin comes from `location.ancestorOrigins` checked against the allowlist; otherwise (Firefox) it posts to each allowed origin and the browser delivers only to the match. A `sessionStorage` guard prevents duplicates on reload. |
| **Salesforce debug mode** | `?debug=1` → hidden `debug` / `debugEmail` fields. The org is resolved the same way as the org config (`?org=`, else `presets.json` `_config`). |
| **reCAPTCHA org fix** | When an org config is applied, `captcha_settings.orgId` is set to the config `oid` (and `keyname` to the optional `captcha_keyname`). Before this, `?org=` posted to the sandbox with the prod orgId in `captcha_settings`, and Salesforce rejected it with "Your Lead could not be processed". |

## 6. Test tooling

### `embed-test.html` (linked from the index: "Embed & Event Test")

Acts as the parent website. It embeds a form in an iframe and shows the `form_submission` event it receives, using the same validation as the handover listener.

| Parameter | Values | Default |
|---|---|---|
| `form` | `LeadForm/index.html`, `CaseForm/index.html`, `LeadForm/CBCForm.html`, `LeadForm/RichForm.html` | Lead Form |
| `mode` | `simulate` (no Salesforce, no reCAPTCHA; the test page loads the thank-you page itself) · `salesforce` (real submit) | `simulate` on localhost, `salesforce` elsewhere |
| `debug` | `1`: shows the "Show POST details" toggle and POST entries (target URL, fields, reCAPTCHA token status), and enables Salesforce debug in the form | off |
| anything else | passed through to the form (`form_id`, `campaign`, `org`, `template`, `branch`, …) | — |

Example: `https://jih-marketing-forms-git-staging-john-i-haas.vercel.app/embed-test.html?form_id=test&debug=1`

Notes:
- Real submits on **localhost** are blocked by Chrome (a public site can't redirect to a local address), so use `simulate` there.
- Vercel **Deployment Protection** must be off for the staging preview. Otherwise the iframe is redirected to the Vercel login page, which can't be framed.

### `parent.html`

The example embedding page now includes the handover listener and `form_id=parent-test`. It loads the form from its own host, so it works on any deployment.

## 7. Verification performed

End-to-end tests in headless Chrome with a local stand-in for Salesforce (records the POST, redirects to `retURL`):

| Scenario | Result |
|---|---|
| Lead form, `form_id` + `campaign` + template | 1 event, `form_type: "lead"` |
| Case form, `form_id` | 1 event, `form_type: "case"` |
| No `form_id` | No event; `retURL` without tracking params |
| Simulate vs real mode, `debug` on/off | As specified |

**Field-by-field POST comparison** across `dabbd50` (before the `version` field), `7d2f299` (last commit before this work) and v4.7, in four scenarios:
- No field was added or removed by this work. The only differences are the `retURL` value and `captcha_settings.orgId` with `?org=`.
- `version=1.1` is the only field not present in older code. It was introduced on 2026-09-10 (`a0c32e1`), before this work.
